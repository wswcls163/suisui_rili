# 岁岁日历 · 技术方案

版本：V0.9｜日期：2026-09-05｜状态：生日、账号与同步代码已实现，Supabase 联调、手机安装包与真机验收待完成

依据：[产品设计文档](product-design.md) 与 [交互 Demo](../demo/README.md)。本方案面向第一期生日功能，重点是手机端交付、便于修改，以及为后续功能保留清晰的接入位置。

## 1. 技术决策与交付范围

正式应用采用 **React Native + Expo + TypeScript + SQLite**，面向 Android 和 iOS，共享业务代码，并分别验证平台行为。应用已放在仓库的 `mobile/` 目录，现有 Web Demo 保留为交互参考。

按后续确认的交付顺序，**手机优先，同时提供可实际操作的电脑浏览器预览**。浏览器通过 React Native Web 复用界面和业务规则，用 IndexedDB 保存本机数据；手机使用 SQLite。未登录数据留在各自设备，登录同一账号后通过 Supabase 同步。浏览器预览可用于亲自测试功能，不能替代手机上的原生模块、安装包和生命周期验收。Windows 独立安装包推迟到手机端稳定后；届时评估复用 Web 界面接入桌面外壳，并处理桌面数据与升级流程。

生日阶段交付增删改查、双历月历、下次生日、本地持久保存和应用内当天提醒；随后增加邮箱账号、服务端迁移和云同步。应用安装完成后，核心功能可离线使用，首次启动为空数据。系统通知、通讯录、桌面小组件和普通日程等预留事项类型仍未实现。

先在当前 Windows 环境开发 Android，并保留 iOS 构建路径。当前 Expo SDK 57 最低支持 Android 7、iOS 16.4。正式分发顺序、签名和渠道按实际测试设备确定，不默认承诺微信小程序、鸿蒙原生应用或网站公网发布。

## 2. 技术栈

| 部分 | 选择 | 使用方式 |
| --- | --- | --- |
| 应用框架 | React Native + Expo | 手机原生界面与构建流程；正式开发采用 development build |
| 语言 | TypeScript，开启 strict | 明确生日、农历日期、计算结果和存储接口的类型 |
| 页面导航 | Expo Router | 管理首页、生日簿、详情和编辑页面；路由文件仅组装页面 |
| 界面与样式 | React Native 基础组件 + StyleSheet + 统一主题变量 | 复用颜色、字号、间距、按钮和卡片，延续 Demo 的视觉方向 |
| 界面状态 | React Hooks、Context、useState | 集中维护生日快照，局部表单状态留在组件内；当前规模无需额外状态库 |
| 本地数据库 | SQLite，通过 expo-sqlite 访问 | 存储原始生日，用版本化迁移管理字段变化 |
| 农历引擎 | lunar-javascript 1.7.7，封装为适配器 | 按独立对照表核验声明范围；页面不直接依赖历法库 |
| 电脑预览存储 | Dexie + IndexedDB | 平台入口选择 Web 仓库，共享页面不判断数据库类型 |
| 认证与云端 | Supabase Auth + PostgreSQL | 邮箱密码认证、按账号隔离生日、版本与幂等写入 |
| 原生会话 | expo-secure-store | 保存认证会话，不保存用户密码 |
| 测试 | Jest / jest-expo + React Native Testing Library | 规则、状态和组件交互测试；原生存储另做设备集成验证 |

导航、本地保存和开发构建参考 [Router 文档](https://docs.expo.dev/router/introduction/)、[SQLite 文档](https://docs.expo.dev/versions/latest/sdk/sqlite/) 和 [development build 文档](https://docs.expo.dev/develop/development-builds/introduction/)。测试环境参考 [Expo 单元测试文档](https://docs.expo.dev/develop/unit-testing/)。

工程使用 Expo SDK 57、React Native 0.86、React 19.2 和匹配的原生模块，提交 npm 锁文件及 `.nvmrc`（Node.js 22.23.2），并用 `expo-doctor` 检查依赖匹配。代码通过 ESLint、Prettier 统一规范。避免分别追逐各依赖的最新版本。Demo 的 Vite、Vinext、浏览器组件和部署配置不迁入手机工程。

月历先用 React Native 基础组件实现七列网格，单日接收阳历、农历标签、生日数量和选中状态，月份计算放在业务模块。第一期不引入完整日程系统。

## 3. 模块边界与建议目录

页面调用应用逻辑，应用逻辑组合农历规则、存储、账号、同步和时钟；SQLite、IndexedDB、Supabase、历法库与手机生命周期分别由适配层接入。纯业务模块不依赖 React Native、数据库或系统通知。

```text
mobile/
  app/                    # Expo Router 路由和页面入口
  src/
    components/           # 月历、生日表单；ui.tsx 合并小组件与主题变量
    core/
      birthday.ts         # 类型、校验、年度生日规则与展示结果
      calendar.ts         # 历法接口、库适配与核验口径
      festivals.ts        # 精选节日、纪念日规则与节气组合，独立于生日和界面
      dates.ts            # 严格日期、月历网格、北京时间
      clock.ts            # 可注入时钟与前台刷新
    state/AppProvider.tsx # CRUD、共享快照、手机生命周期接入
    state/AuthProvider.tsx # 会话与认证动作
    state/SyncProvider.tsx # 数据范围、同步时机、冲突与退出保护
    auth/                 # Supabase 客户端与会话存储
    sync/                 # 同步模型、协调器与远端适配器
    data/
      sqlite.ts           # SQLite 仓库与迁移，真实 SQL 可单独测试
      web.ts              # IndexedDB 仓库
      repository.ts      # 原生平台入口
      repository.web.ts  # 浏览器平台入口
    types/                # 历法库所用 API 的类型声明
  tests/                  # 规则、组件、存储集成测试及历法核验数据
  scripts/                # 历法对照数据抓取、核验与图标生成
```

这是职责划分，不为每个函数创建单独文件。当前保持一个 Expo 工程，通过平台文件扩展名选择存储；不建立多包仓库、通用服务层或空的未来模块。农历与生日逻辑不依赖界面，可以独立运行和测试。

“日历”和“生日簿”读取同一份生日状态。选中日期、浏览月份与真实今天分别保存。新增类型通过简单的事项类型目录展示，未开放类型在界面和业务入口都不能提交。

生日标题由 `core/birthday.ts` 的纯函数 `birthdayTitle` 统一生成：原始姓名以“生日”结尾时直接使用，否则追加“的生日”。页面、无障碍标签、保存与删除提示复用该规则；数据库与编辑表单保留原始姓名，不做数据迁移，也不把展示标题回写为姓名。

`components/DateJumpDialog.tsx` 将日期跳转弹窗与内部滚轮放在同一文件，使用基础 ScrollView、固定行高和滚动停止后的对齐，不新增依赖。弹窗只保存日期草稿，年份限制在声明范围内；年月变化复用 `dates.ts` 的月末规则调整日数。确认通过现有 `selectDate` 同步月份与选日，关闭时丢弃草稿并清理滚动计时器。手机支持滑动和点选；Web 补充滚轮吸附、键盘操作和当前值的无障碍属性，较矮窗口显示三行，其余显示五行。

常见节日由 `core/festivals.ts` 维护精选名称与规则：固定阳历节日按月日匹配，传统节日匹配普通农历月日，除夕取下一次春节前一天；南北小年分别取腊月廿三、廿四。三个历史纪念日包含月日、全称和起始年份，避免标注到事件发生以前。二十四节气通过 `core/calendar.ts` 的 `solarTermOn` 查询，按阳历年缓存，明确处理历法库“冬至”键指向上一年的约定。

返回列表按传统节日、固定阳历节日、纪念日、节气排列，清明统一由节气产生。网格直接显示首项名称和额外数量；名称使用统一 10 号字、单行尾部省略，不做简称转换或按长度缩小字号。选日面板与无障碍标签展示全部名称及原始农历日期。标注不写入生日数据库，不改变提醒或事项数量。节气与天文台 1901—2100 年的 4,800 条独立记录逐日核验，包含无节气日期；6 处日界差异统一采用天文台表口径，详情见[历法核验数据](../mobile/tests/fixtures/README.md)。

## 4. 数据模型与持久保存

第一期使用一张 `birthdays` 表，一人一条记录。业务模型为 `{ name, lunar, solar }`，两套日期分别可为空但不能同时为空；不额外保存可由字段推导出的生日方式。固定阳历月日是用户输入的独立生日，不是逐年换算得到的阳历日期。

| 字段 | 含义与约束 |
| --- | --- |
| id | 创建时生成的 UUID，修改生日不更换 ID |
| name | 去除首尾空白后的称呼，1—30 个字符，允许不同记录重名 |
| lunarMonth / lunarDay | 原始农历月日；业务层对应 `lunar.month / lunar.day`，有效范围为 1—12、1—30 |
| isLeap | 原始闰月标记；业务层对应 `lunar.isLeap`，SQLite 为 0 或 1；不使用农历时三个农历字段均为空 |
| solarMonth / solarDay | 固定阳历月日；业务层对应 `solar.month / solar.day`，允许 2 月 29 日，不使用阳历时两个字段均为空 |
| createdAt / updatedAt | UTC 时间戳，记录创建、修改时间，不参与生日日期计算 |

当前不保存出生年份或年龄，头像颜色可由 ID 派生。数据库设置主键、非空和日期范围约束，所有用户输入通过参数绑定写入。

应用通过 `BirthdayRepository` 的查询、新增、修改、删除方法访问数据。SQLite 是持久数据来源，内存状态是已提交数据的快照。写入期间避免重复提交，事务成功后再更新共享状态、关闭表单并提示成功；失败时保留输入并提供重试入口。更新或删除不存在的 ID 时返回明确结果，不能默认为成功。

启动时先打开数据库、完成迁移，再加载生日。使用数据库版本号和顺序迁移，迁移操作与版本更新在事务内完成。升级失败不能自动删库重建，读取失败不能显示为首次使用的空列表；遇到无法识别的更高数据库版本时停止写入并提示升级应用，避免旧应用破坏新数据。

双生日将 SQLite 与 IndexedDB 升级至版本 2。SQLite 在事务内建立新约束表、复制旧农历字段和原始身份信息，再替换表和版本号；IndexedDB 使用 Dexie 升级事务，将旧月日放入 `lunar` 并设置 `solar: null`。不从姓名或本年度换算推断阳历生日。集成测试覆盖真实 v1 数据升级、失败回滚、双生日重开、切换方式、高版本保护和日期约束。

账号同步将两种本地仓库升级至版本 3，增加 `ownerKey`、远端版本、软删除时间、`sync_outbox` 和 `sync_conflicts`。旧记录统一进入访客范围；账号记录与队列在一次事务中写入。退出账号只清理该账号的本机缓存，访客数据保持独立。完整字段、服务端表和冲突规则见[账号登录技术方案](account-login-technical-design.md)。

本地保存支持正常关闭和重启，不等于跨设备备份。卸载、清理应用数据或设备丢失可能导致记录丢失。第一期不承诺恢复能力，导入导出和云备份作为后续功能规划。

## 5. 农历引擎与年度生日规则

历法适配器负责阳历转农历、查询指定农历月份的月首和天数，通过月首加日序得到阳历结果。采用 [lunar-javascript](https://github.com/6tail/lunar-javascript) 并封装项目使用的类型，不能将 Demo 的有限历表直接当作正式引擎。原生打包检查已通过，运行表现仍需真机确认。

生日模块在适配器之上执行以下规则：

1. 普通月生日只选择当年的普通月份。
2. 闰月生日在当年有对应闰月时选择闰月，否则选择普通月份，并记录回退原因。
3. 确定适用月份后，如果原始日为三十而该月只有二十九天，采用二十九，并记录提前原因。
4. 换算为阳历日期，返回该次结果，始终保留原始生日不变。

年度结果包含阳历日期、生日类型列表、可为空的实际农历年与月日、调整原因代码。农历使用原有年度规则；阳历单独按指定年份拼接原始月日，2 月 29 日遇平年取 28 日并记录 `solar-leap-day`，不修改原始输入。

`upcoming` 分别从当前农历年、当前阳历年寻找不早于起点的候选结果，然后按阳历日期合并同一个人的同日结果、排序并截取。纯阳历生日不调用农历引擎。月历从所查看月份的第一天计算并筛选到月末，包含当月已经过去的生日；事项 ID 使用人物 ID 与阳历日期，同日双生日合并后仍只有一个 ID。生日簿每人一行，按最近一次排序；当天提醒使用同一结果，避免重复计数。

应用支持 **阳历 1901-01-01 至 2100-12-31**。已对 73,049 个日期及涉及的 2,475 个农历月份进行香港天文台公开对照表核验，包括 1901 年初涉及的上一农历年。天文台原文中 2069-12-30 缺行，按前后连续日序补出并明确标记；2057 年九月初一与库存在一天差异，统一采用天文台表口径，同时调整两个方向的计算。校正后比对无差异，出处、原文摘要和处理说明见[历法核验数据](../mobile/tests/fixtures/README.md)。不能据此声称手机平台验收也已完成。

范围外日期不可选。范围内未找到下次生日时返回“超出支持范围”状态，在列表中排到有日期记录之后，生日仍可编辑和删除。详情展示未来若干次生日，接近范围末尾时允许不足，不能越界猜测或导致整页失败。

用 [香港天文台公历与农历对照表](https://www.hko.gov.hk/en/gts/time/conversion.htm) 等独立资料核验，保存测试样本的来源、年份与核验结果。历法库自身输出和同源库互相比对不能单独证明正确性；发现差异时记录具体日期并核实口径。

## 6. 日期、时区和应用内提醒

第一期统一以 **Asia/Shanghai（UTC+08:00）** 判断今天。手机在其他时区时也使用这一口径，在日期说明中明确“按北京时间计算”。未来增加时区选择时，由时钟模块集中处理。

阳历业务日期使用严格校验的 `YYYY-MM-DD`，农历使用年、月、日、闰月字段。生日是一条日期规则，不作为时间戳保存。剩余天数按两个日期的整数日序相减，不按设备本地午夜的毫秒差取整。

用可注入的 `Clock` 提供当前时间，正式环境读取设备时间，测试环境可固定或推进时间。离线时依赖设备时钟，不承诺校验手机设置的时间是否准确。

提醒由“已保存生日 + 今天”计算，在以下时机重新检查：

- 冷启动并完成数据库加载后。
- 从后台恢复前台，或重新进入首页时。
- 生日新增、修改、删除成功后。
- 前台持续打开时，在北京时间下一次午夜安排刷新；以低频检查（例如每分钟）补偿计时器延迟或设备时间变化。

进入后台时清理前台计时器，恢复后重新读取现在并安排检查。选日和翻月不修改今天状态。第一期不申请系统通知权限，不依赖后台任务维持提醒。

## 7. 手机界面与 Demo 迁移

首页保留“日历 / 生日簿”入口和顶部当天提醒。手机竖屏中，月历下方展示所选日期的事项；新增和编辑采用手机页面或模态面板。适配安全区域、键盘遮挡、系统返回和文字放大。

同日多人的生日全部在事项列表中列出，网格单元只展示有限姓名和数量提示。编辑时读取原始生日，新建时才由选中阳历日期预填。

月历生日名称下方使用独立一行显示 `occurrence.kinds` 对应的“农历”“阳历”，按本次发生类型标注，不根据人物是否同时保存两套日期推断。类型标记可换行，长姓名只在名称行尾部省略；生日区预留相同高度，使有无生日的格子保持日期对齐。

表单提供三种生日方式，复用现有月日选择组件；农历与阳历各有独立输入缓冲，切换方式不丢失当前草稿，保存时只提交启用的日期。补充缺失日期需要主动选择，避免误用当前浏览日期。双生日分别展示下一次预览；详情按时间列出接下来的三次生日并注明类型，同一天重合时合并说明。

| Demo 内容 | 处理方式 |
| --- | --- |
| 产品流程、文案、颜色和布局意图 | 作为手机端设计参考 |
| TypeScript 类型、校验、日期规则与测试用例 | 按新模块边界整理复用，保留有价值的边界用例 |
| HTML、CSS、shadcn / Base UI、React DayPicker | 用 React Native 组件重建，不能直接复用网页组件 |
| 模拟今天、种子数据、演示场景、有限历表 | 仅留作测试材料，不进入正式启动流程 |
| WebMCP 与 Sites / Vinext 配置 | 保留在 Demo，不作为手机运行依赖 |

迁移以用户行为和计算规则一致为目标，不要求与 Demo 使用相同目录。Demo 测试通过不代表手机界面、SQLite 或原生构建已验证。

| 纪念日、倒数日等 | 增加独立数据与规则，向月历输出统一展示结果，复用合适的界面组件 |
| 桌面小组件 | 复用生日计算结果，分别评估 Android / iOS 的展示、数据共享与刷新机制 |

后续本地通知优先评估 [expo-notifications](https://docs.expo.dev/versions/latest/sdk/notifications/)。农历生日需逐年换算后安排具体阳历日期的通知，不能设置成固定阳历月日的年度重复；还需处理权限、排程数量限制、取消与补排，并在目标真机验证。不为未来能力预先创建空业务表或安装无关模块。

## 9. 测试与验收

| 验证层次 | 必须覆盖的内容 |
| --- | --- |
| 历法与规则单元测试 | 普通月不重复、闰月存在或缺失、小月三十、规则组合、原始生日不变、阳历与农历跨年、支持范围边界 |
| 独立历法核验 | 来源可追溯的已知日期样本及声明范围内批量比对，重点检查闰月、月末和年度边界 |
| 节日、节气与纪念日 | 南北小年跨年、24 节气与相邻日、冬至年度边界、纪念日起始年、同日多项和生日共存、网格统一字号及尾部省略、选日全称 |
| 日期与状态测试 | 固定时区、选日与今天隔离、跨午夜、前后台恢复、设备时间修改后的刷新、下次生日排序 |
| 存储与同步集成测试 | 真实 SQLite 与 fake-indexeddb 的增删改查、迁移与回滚、账号隔离、离线队列、首次合并、完整拉取、软删除和冲突解决 |
| 组件交互测试 | 日期预填、同日多人、空状态、编辑回填、删除确认、日期滚轮，以及邮箱校验、账号表单、会话恢复、回调和首次同步状态 |
| 真机与构建验证 | Android / iOS 冷启动、杀进程后数据保留、离线使用、前后台切换、键盘与返回、文字放大及发布构建 |

模拟数据库和时钟用于测试逻辑，不替代真实 SQLite 与设备生命周期验证。声明某个平台可发布前，必须完成该平台的设备验证；只有 Android 结果时不宣称 iOS 已通过。

每次实现改动同步编写或更新测试，执行完整自动测试、类型检查、Lint 和受影响的构建及设备验证，通过后创建对应 Git commit。数据库迁移或历法库升级必须补充旧数据和日期回归验证。

文档链接测试从仓库根目录运行 `node --test tests/*.test.mjs`，应用测试和构建命令见 [mobile/README.md](../mobile/README.md)。目前包含 168 项 Jest 测试、20 项存储与同步集成测试及独立历法批量核验。真实 SQLite 仓库测试在 Node SQLite 引擎上运行；Supabase 测试当前检查迁移和权限结构，真实 RLS、邮件与跨设备流程待开发项目联调。expo-sqlite 原生桥接、真机离线和杀进程场景留在设备验收中单独记录。[验证记录](validation.md) 区分已通过检查与尚未执行的设备验收。

## 10. 实施顺序

1. **建立手机工程与运行验证。** 创建 Expo 工程，锁定工具链，打通 Android 开发构建并尽早验证 iOS；小范围验证 SQLite 和农历库在真机的运行。
2. **完成规则与存储。** 实现时区、历法适配器、年度生日计算、数据库迁移和仓库接口，让规则与持久保存通过测试。
3. **实现第一期界面。** 完成月历、生日簿、详情和新建编辑，接入统一状态与真实今天，移除正式流程中的演示数据。
4. **接入账号与同步。** 完成认证、本地数据范围、离线队列、服务端迁移、冲突处理和账号管理。
5. **完成设备验收。** 检查跨午夜、重启保留、失败恢复、账号深链接、跨设备同步和手机交互，完成目标平台发布构建。

当前第 2、3、4 步的代码与自动测试已完成，电脑预览已走通真实 CRUD 和账号入口；第 1 步完成工程初始化、Android 原生工程生成和双平台 Hermes 资源导出，但本机缺少 Android SDK，尚未完成安装包编译。第 4 步仍需 Supabase 开发项目完成真实云端联调，第 5 步的设备验收待具备工具链和测试手机后执行。

iOS 本地构建和模拟器需要 macOS / Xcode；Windows 环境也可选择 EAS Build 云构建，配合真实 iPhone 验证。云服务是可选工具，其账号、签名、费用与分发条件在实际使用时确定，当前未上传工程或发布应用。参见 [Expo FAQ](https://docs.expo.dev/faq/) 与 [EAS Build 文档](https://docs.expo.dev/build/introduction/)。
