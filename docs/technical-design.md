# 岁岁日历 · 技术方案

版本：V2.0｜日期：2026-10-07｜状态：生日、可选出生年份与周岁、未来选日距离、时光记、节日合并提醒、原生可靠排程、品牌通知卡片、带系统提示音与短振动的顶部横幅、可选锁屏全屏提醒、全局功能菜单和账号同步均已实现；Android 0.3.5 已在 ColorOS 16 真机完成覆盖安装与前台顶部横幅验证，用户反馈已测试的核心提醒行为满足当前需求，厂商强停等平台边界仍按验证清单处理

依据：[产品设计文档](product-design.md)。本方案面向第一期生日功能，重点是手机端交付、便于修改，以及为后续功能保留清晰的接入位置。

## 1. 技术决策与交付范围

正式应用采用 **React Native + Expo + TypeScript + SQLite**，面向 Android 和 iOS，共享业务代码，并分别验证平台行为。应用位于仓库的 `mobile/` 目录；早期 Web 交互原型已于 2026-10-07 移除，避免继续维护两套界面与生日规则。

按后续确认的交付顺序，**手机优先，同时提供可实际操作的电脑浏览器预览**。浏览器通过 React Native Web 复用界面和业务规则，用 IndexedDB 保存本机数据；手机使用 SQLite。未登录数据留在各自设备，登录同一账号后通过 Supabase 同步。浏览器预览可用于亲自测试功能，不能替代手机上的原生模块、安装包和生命周期验收。Windows 独立安装包推迟到手机端稳定后；届时评估复用 Web 界面接入桌面外壳，并处理桌面数据与升级流程。

生日阶段交付增删改查、双历月历、下次生日、本地持久保存和应用内当天提醒；随后增加邮箱账号、服务端迁移、云同步和设备本地系统通知。时光记作为独立实体接入同一仓库与同步通道，按开始日期和北京时间计算天数或周年。应用安装完成后，核心功能可离线使用，首次启动为空数据。通讯录、桌面小组件和普通日程等预留事项类型仍未实现。

先在当前 Windows 环境开发 Android，并保留 iOS 构建路径。当前 Expo SDK 57 最低支持 Android 7、iOS 16.4。正式分发顺序、签名和渠道按实际测试设备确定，不默认承诺微信小程序、鸿蒙原生应用或网站公网发布。

Windows 本地 Android 构建使用完整 JDK 17、Android SDK / Build Tools 36 和 NDK 27.1.12297006。原生目录仍由 Expo 生成并保持 Git 忽略；当前工程所在路径包含中文，而该版本 JDK / Gradle / Expo 自动链接在 Windows 上不能稳定贯穿 Unicode 物理路径，因此发布构建将 `mobile/` 输入复制到纯英文临时目录、按同一 `package-lock.json` 执行 `npm ci` 后再运行 `app:assembleRelease`。临时目录只解决工具链路径兼容，不是新的源码来源。测试 APK 使用 Android Debug 证书，仅用于安装验收；正式发布前必须改为独立的安全签名配置，且签名文件和密码不得进入仓库。

月历先用 React Native 基础组件实现七列网格，单日接收阳历、农历标签、生日数量和选中状态，月份计算放在业务模块。第一期不引入完整日程系统。

## 3. 模块边界与建议目录

页面调用应用逻辑，应用逻辑组合农历规则、存储、账号、同步和时钟；SQLite、IndexedDB、Supabase、历法库与手机生命周期分别由适配层接入。纯业务模块不依赖 React Native、数据库或系统通知。

```text
mobile/
  app/                    # Expo Router 路由和页面入口
  src/
    components/           # 月历、表单、临时日期计算和左侧功能菜单；ui.tsx 合并小组件与主题变量
    core/
      birthday.ts         # 类型、校验、年度生日规则与展示结果
      countup.ts          # 时光记类型、校验、自然日与周年计算规则
      calendar.ts         # 历法接口、库适配与核验口径
      festivals.ts        # 精选节日、纪念日规则与节气组合，独立于生日和界面
      dates.ts            # 严格日期、月历网格、北京时间
      clock.ts            # 可注入时钟与前台刷新
      notification.ts     # 节日、生日与周年的北京时间通知计划及同日合并
    notifications/       # 原生排程、Web 预览替身和设备本地设置
    state/AppProvider.tsx # CRUD、共享快照、手机生命周期接入
    state/NotificationProvider.tsx # 权限、设置持久化与数据变化后的重排
    state/AuthProvider.tsx # 会话与认证动作
    state/SyncProvider.tsx # 数据范围、同步时机、冲突与退出保护
    auth/                 # Supabase 客户端与会话存储
    sync/                 # 同步模型、协调器与远端适配器
    data/
      sqlite.ts           # SQLite 仓库与迁移，真实 SQL 可单独测试
      web.ts              # IndexedDB 仓库
      repository.ts      # 原生平台入口
      repository.web.ts  # 浏览器平台入口
    types/                # 历法库所用 API 的类型声明
  tests/                  # 规则、组件、存储集成测试及历法核验数据
  scripts/                # 历法对照数据抓取、核验与图标生成
```

这是职责划分，不为每个函数创建单独文件。当前保持一个 Expo 工程，通过平台文件扩展名选择存储；不建立多包仓库、通用服务层或空的未来模块。农历与生日逻辑不依赖界面，可以独立运行和测试。

“日历”和“生日簿”读取同一份生日状态，“时光记”读取独立的时光记集合。选中日期、浏览月份与真实今天分别保存；同一个 `TodayWatcher` 在跨午夜和恢复前台时刷新节日与生日提醒、累计天数和周年倒计时。新增类型通过简单的事项类型目录展示，未开放类型在界面和业务入口都不能提交。

时光记继续使用兼容标识 `type: 'countup'`，保存标题、`YYYY-MM-DD` 开始日期、可选备注和 `displayMode`。`days` 的显示序号为 `today - startDate + 1`，因此开始当天为第 1 天；`anniversary` 根据开始月日计算已满周年和下一周年，2 月 29 日在平年回退到 2 月 28 日。开始日在未来时，两种方式都展示距离开始的自然日数。纯计算位于 `core/countup.ts`，不依赖界面或存储。

`components/DateCalculatorDialog.tsx` 是首页直接打开的临时日期计算器。年、月、日使用三个独立的组件本地状态，月份和日期接受 1—2 位数字；只有计算时才补齐为严格的 `YYYY-MM-DD`，因此删除或修改一个字段不会重排其他字段。有效日期通过 `dates.ts` 的 UTC 自然日序号相减得到有符号天数：过去、今天和未来分别转换为对应文案；近似年数使用绝对天数除以公历平均年长 365.2425 天并保留两位小数，不能替代精确天数。组件不调用 `AppProvider` 的 CRUD、数据库仓库或同步层，关闭即丢弃输入，保证查询不会成为事项记录。

生日标题由 `core/birthday.ts` 的纯函数 `birthdayTitle` 统一生成：原始姓名以“生日”结尾时直接使用，否则追加“的生日”。页面、无障碍标签、保存与删除提示复用该规则；数据库与编辑表单保留原始姓名，不做数据迁移，也不把展示标题回写为姓名。

`components/DateJumpDialog.tsx` 将日期跳转弹窗与内部滚轮放在同一文件，使用基础 ScrollView、固定行高和滚动停止后的对齐，不新增依赖。弹窗只保存日期草稿，年份限制在声明范围内；年月变化复用 `dates.ts` 的月末规则调整日数。确认通过现有 `selectDate` 同步月份与选日，关闭时丢弃草稿并清理滚动计时器。手机支持滑动和点选；Web 补充滚轮吸附、键盘操作和当前值的无障碍属性，较矮窗口显示三行，其余显示五行。

常见节日由 `core/festivals.ts` 维护精选名称与规则：固定阳历节日按月日匹配，传统节日匹配普通农历月日，除夕取下一次春节前一天；南北小年分别取腊月廿三、廿四。三个历史纪念日包含月日、全称和起始年份，避免标注到事件发生以前。二十四节气通过 `core/calendar.ts` 的 `solarTermOn` 查询，按阳历年缓存，明确处理历法库“冬至”键指向上一年的约定。

返回列表按传统节日、固定阳历节日、纪念日、节气排列，清明统一由节气产生。网格直接显示首项名称和额外数量；名称使用统一 10 号字、单行尾部省略，不做简称转换或按长度缩小字号。选日面板与无障碍标签展示全部名称及原始农历日期。标注不写入生日数据库，不改变事项数量，但同一份返回列表会供首页当天卡片和系统通知计划使用，避免界面标注与提醒范围不一致。节气与天文台 1901—2100 年的 4,800 条独立记录逐日核验，包含无节气日期；6 处日界差异统一采用天文台表口径，详情见[历法核验数据](../mobile/tests/fixtures/README.md)。

## 4. 数据模型与持久保存

本地延续 `birthdays` 表以兼容已发布数据，并由 `itemType` 区分生日与时光记。生日业务模型为 `{ name, lunar, solar, birthYear }`，两套日期分别可为空但不能同时为空，`birthYear` 为可空的阳历出生年份；时光记模型为 `{ type: 'countup', title, startDate, note, displayMode }`。固定阳历月日是用户输入的独立生日，不是逐年换算得到的阳历日期。

| 字段                                      | 含义与约束                                                                                                             |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| id                                        | 创建时生成的 UUID，修改生日不更换 ID                                                                                   |
| name                                      | 去除首尾空白后的称呼，1—30 个字符，允许不同记录重名                                                                    |
| lunarMonth / lunarDay                     | 原始农历月日；业务层对应 `lunar.month / lunar.day`，有效范围为 1—12、1—30                                              |
| isLeap                                    | 原始闰月标记；业务层对应 `lunar.isLeap`，SQLite 为 0 或 1；不使用农历时三个农历字段均为空                              |
| solarMonth / solarDay                     | 固定阳历月日；业务层对应 `solar.month / solar.day`，允许 2 月 29 日，不使用阳历时两个字段均为空                        |
| birthYear                                 | 可选阳历出生年份，空值表示不显示年龄；保存范围 1901—2100，表单进一步限制不得晚于北京时间今天所在年份                   |
| itemType / startDate / note / displayMode | `birthday` 或 `countup`；时光记必须有开始日期且生日字段为空，备注不超过 120 字；展示方式只允许 `days` 或 `anniversary` |
| createdAt / updatedAt                     | UTC 时间戳，记录创建、修改时间，不参与生日日期计算                                                                     |

年龄不单独保存。每次生日发生时使用 `发生阳历年份 - birthYear` 计算实足周岁；字段缺失或结果为负数时隐藏年龄。数据库设置主键、非空和日期范围约束，所有用户输入通过参数绑定写入。

应用通过组合的生日与时光记仓库接口查询、新增、修改和删除数据。SQLite 是持久数据来源，内存状态是已提交数据的快照。写入期间避免重复提交，事务成功后再更新共享状态、关闭表单并提示成功；失败时保留输入并提供重试入口。更新或删除不存在的 ID 时返回明确结果，不能默认为成功。

启动时先打开数据库、完成迁移，再加载生日。使用数据库版本号和顺序迁移，迁移操作与版本更新在事务内完成。升级失败不能自动删库重建，读取失败不能显示为首次使用的空列表；遇到无法识别的更高数据库版本时停止写入并提示升级应用，避免旧应用破坏新数据。

双生日将 SQLite 与 IndexedDB 升级至版本 2。SQLite 在事务内建立新约束表、复制旧农历字段和原始身份信息，再替换表和版本号；IndexedDB 使用 Dexie 升级事务，将旧月日放入 `lunar` 并设置 `solar: null`。不从姓名或本年度换算推断阳历生日。集成测试覆盖真实 v1 数据升级、失败回滚、双生日重开、切换方式、高版本保护和日期约束。

账号同步将两种本地仓库升级至版本 3，增加 `ownerKey`、远端版本、软删除时间、`sync_outbox` 和 `sync_conflicts`。版本 4 增加事项类型、开始日期和备注，版本 5 增加 `displayMode`，版本 6 增加可空的 `birthYear`；v5 及更早生日升级后该字段为 `null`。旧生日保留原 ID、日期和时间戳，原累计日升级后默认使用 `days`。生日与时光记共用账号范围、软删除、离线队列和冲突处理。退出账号只清理该账号的本机缓存，访客数据保持独立。完整字段、服务端表和冲突规则见[账号登录技术方案](account-login-technical-design.md)。

本地保存支持正常关闭和重启，不等于跨设备备份。卸载、清理应用数据或设备丢失可能导致记录丢失。第一期不承诺恢复能力，导入导出和云备份作为后续功能规划。

## 5. 农历引擎与年度生日规则

历法适配器负责阳历转农历、查询指定农历月份的月首和天数，通过月首加日序得到阳历结果。采用 [lunar-javascript](https://github.com/6tail/lunar-javascript) 并封装项目使用的类型，正式规则由独立对照数据验证。原生打包检查已通过，运行表现仍需真机确认。

生日模块在适配器之上执行以下规则：

1. 普通月生日只选择当年的普通月份。
2. 闰月生日在当年有对应闰月时选择闰月，否则选择普通月份，并记录回退原因。
3. 确定适用月份后，如果原始日为三十而该月只有二十九天，采用二十九，并记录提前原因。
4. 换算为阳历日期，返回该次结果，始终保留原始生日不变。

年度结果包含阳历日期、生日类型列表、可为空的实际农历年与月日、调整原因代码。农历使用原有年度规则；阳历单独按指定年份拼接原始月日，2 月 29 日遇平年取 28 日并记录 `solar-leap-day`，不修改原始输入。

`upcoming` 分别从当前农历年、当前阳历年寻找不早于起点的候选结果，然后按阳历日期合并同一个人的同日结果、排序并截取。纯阳历生日不调用农历引擎。月历从所查看月份的第一天计算并筛选到月末，包含当月已经过去的生日；事项 ID 使用人物 ID 与阳历日期，同日双生日合并后仍只有一个 ID。生日簿每人一行，按最近一次排序；当天提醒使用同一结果，避免重复计数。

应用支持 **阳历 1901-01-01 至 2100-12-31**。已对 73,049 个日期及涉及的 2,475 个农历月份进行香港天文台公开对照表核验，包括 1901 年初涉及的上一农历年。天文台原文中 2069-12-30 缺行，按前后连续日序补出并明确标记；2057 年九月初一与库存在一天差异，统一采用天文台表口径，同时调整两个方向的计算。校正后比对无差异，出处、原文摘要和处理说明见[历法核验数据](../mobile/tests/fixtures/README.md)。不能据此声称手机平台验收也已完成。

范围外日期不可选。范围内未找到下次生日时返回“超出支持范围”状态，在列表中排到有日期记录之后，生日仍可编辑和删除。详情展示未来若干次生日，接近范围末尾时允许不足，不能越界猜测或导致整页失败。

用 [香港天文台公历与农历对照表](https://www.hko.gov.hk/en/gts/time/conversion.htm) 等独立资料核验，保存测试样本的来源、年份与核验结果。历法库自身输出和同源库互相比对不能单独证明正确性；发现差异时记录具体日期并核实口径。

## 6. 日期、时区和提醒

第一期统一以 **Asia/Shanghai（UTC+08:00）** 判断今天。手机在其他时区时也使用这一口径，在日期说明中明确“按北京时间计算”。未来增加时区选择时，由时钟模块集中处理。

阳历业务日期使用严格校验的 `YYYY-MM-DD`，农历使用年、月、日、闰月字段。生日是一条日期规则，不作为时间戳保存。剩余天数与未来选日距离按两个 UTC 整数日序相减，不按设备本地午夜的毫秒差取整。首页中文星期也由该日序生成，不使用设备区域设置，避免语言和时区漂移。

用可注入的 `Clock` 提供当前时间，正式环境读取设备时间，测试环境可固定或推进时间。离线时依赖设备时钟，不承诺校验手机设置的时间是否准确。

应用内提醒由“月历标注 + 已保存生日 + 今天”计算，在以下时机重新检查：

- 冷启动并完成数据库加载后。
- 从后台恢复前台，或重新进入首页时。
- 生日新增、修改、删除成功后。
- 前台持续打开时，在北京时间下一次午夜安排刷新；以低频检查（例如每分钟）补偿计时器延迟或设备时间变化。

进入后台时清理前台计时器，恢复后重新读取现在并安排检查。选日和翻月不修改今天状态。

系统通知由 `core/notification.ts` 生成纯计划，业务层不依赖 Expo。计划始终把 `YYYY-MM-DD + 用户设定时分` 转为 UTC+08:00 的绝对时间：从 `festivalsOn` 逐日取得月历标注，生日的农历和阳历分别逐年计算，时光记只消费 `displayMode: anniversary` 并每年处理 2 月 29 日回退，`days` 不产生通知。所有候选项按 `YYYY-MM-DD` 分组；同日多个节日、生日或周年统一生成一条 `combined` 通知并完整拼接正文。计划按触发时间排序并截取最近 60 条，既为用户预排后续日期，也保留在 iOS 待处理通知上限之内。

Android 不再依赖 Expo 的一次性日期触发链路。`notifications/scheduler.ts` 只负责权限、跨平台分流与结果校验，生产计划通过 `modules/suisui-notification-reliability` 交给 `AlarmManager`；模块以稳定标识持久化最多 60 条生产任务，使用 `setExactAndAllowWhileIdle`，精确权限不可用时诚实降级到 `setAndAllowWhileIdle`。重排只替换生产所有者，保留固定标识的诊断任务；升级时额外清理 0.3.0 遗留的 Expo 生产任务，避免重复。Android 没有公开的闹钟枚举 API，因此“登记回读”核对持久化记录和对应 `PendingIntent` 是否存在，不把 JavaScript API 未抛错等同于系统已登记。

普通通知权限只走 Android 官方 `POST_NOTIFICATIONS` 流程：用户打开“重要日期提醒”时先创建渠道，再调用系统授权 API；用户在系统框点击“允许”后才保存已开启状态并排程。应用不能静默授权，也不能代替用户点击系统按钮。该流程不依赖 ColorOS 私有页面；精确闹钟与全屏意图属于 Android 特殊权限，只有能力缺失时才展示对应系统入口。

`SuisuiAlarmReceiver` 在触发后直接调用 `NotificationManager`，不要求 JavaScript、React Native 或应用进程预先运行，并持久化最近一次原生投递时间。`SuisuiScheduleRestoreReceiver` 监听 `BOOT_COMPLETED`、厂商快速重启、`MY_PACKAGE_REPLACED` 和限定为本包的 `PACKAGE_REPLACED`，重建仍在有效期内的系统闹钟并记录恢复结果；24 小时内错过的提醒会在恢复后补触发，更早的过期任务清理。正常后台、系统回收和锁屏均由原生链路负责；Android“强行停止”仍会冻结闹钟和接收器，重新打开应用后才能恢复，这是平台不可绕过的边界。标准 Android 的最近任务划掉不等同强行停止，但 OnePlus PJE110 的 ColorOS 16 实测会执行 `o-stop(40)`、设置 `stopped=true` 并取消该 UID 的全部 61 个闹钟；同机覆盖安装时系统虽生成更新广播记录，也没有启动应用进程执行接收器。这类设备必须返回桌面而不是划掉，并在升级后打开一次应用；应用只能在获得系统执行机会后恢复，不能自行越过厂商强停策略。

0.3.5 使用不可变的新渠道 `important-dates-popup-v5`：请求 `HIGH`、公开锁屏可见性，启用系统默认提示音和一次 220ms 短振动。0.3.1 曾调用 `NotificationCompat.Builder.setSilent(true)`，ColorOS 16 因此加入 `FLAG_SILENT` 并把通知实际降为 `DEFAULT`；0.3.2 移除通知级静默后，0.3.3 真机渠道虽为 importance 4、`mShowBanner=true`，但渠道仍完全静音，ColorOS 依旧只显示状态栏图标。0.3.4 改用系统提示音后，真机通道已显示“静默通知”关闭，但测试手机处于振动模式且渠道自身禁用振动，系统仍未展示顶部横幅。v5 因此同时保留声音和短振动，确保振动模式下仍产生实际提醒；旧渠道属性不可变，不能复用 v4。ColorOS 还把应用级“横幅”作为独立用户开关：它关闭时通知只进入通知栏，勾选后同一 v5 通知立即显示顶部横幅。该厂商开关没有统一读取或写入 API，所以模块用 `ACTION_APP_NOTIFICATION_SETTINGS` 打开应用级通知页，界面明确提示用户勾选“横幅”并保持“静默通知”关闭，不伪报已允许，也不尝试绕过系统授权。

Android 通知内容使用模块内的 `RemoteViews` 和 `NotificationCompat.DecoratedCustomViewStyle`，分别设置 48dp 折叠内容、76dp 顶部横幅内容和展开内容，避免把横幅布局直接塞进较矮的折叠区域而发生裁切。合并通知由公共 `importantDateTitle` 规则把具体日期内容提升为主标题：两项以内完整显示，超过两项先显示前两项并追加“等重要日子”；顶部横幅为主标题保留两行，正文详情留在展开态。卡片只负责品牌绿色背景、日历图标、提醒类型、日期徽标、标题、正文和展开操作；基础 `setContentTitle` / `setContentText` 继续保留为系统兼容回退。点击卡片或展开操作都进入应用。Android 12 及以上会强制保留系统通知装饰，外层圆角、应用名、时间和可用高度由 Android 或 ColorOS 决定；设置页不再展示模拟通知卡片，真机系统显示是唯一验收依据。

设置页把测试拆为两层：“立即测试顶部横幅”直接调用 `NotificationManager.notify`，每次把当前毫秒时间加入标识，确保系统按新通知而不是旧通知更新处理；“1 分钟后锁屏测试”使用与生产提醒相同的 AlarmManager、持久化和广播链路，登记后显示预计触发时间、稳定标识与回读结果。诊断同时展示应用通知总开关、渠道 importance、声音、振动、精确提醒、原生任务数量、最近测试登记和最近原生投递。模拟横幅预览已移除，避免把应用内绘制结果误当作系统最终外观；真机系统横幅是唯一验收依据。

锁屏全屏默认关闭，用户必须在应用设置中明确开启。开启后生产提醒和锁屏测试使用 `CATEGORY_ALARM` 与 `fullScreenIntent`；`SuisuiReminderActivity` 只设置 `showWhenLocked`、`turnScreenOn` 和排除最近任务，提供关闭按钮，不请求解锁也不绕过密码。Android 14+ 通过 `NotificationManager.canUseFullScreenIntent()` 检测资格，并提供 `ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` 设置入口；无资格时降级为普通通知。测试包包含 `USE_FULL_SCREEN_INTENT` 与 `WAKE_LOCK`，但 Google Play 通常只允许以闹钟或来电为核心用途的应用使用该能力，正式上架前必须重新评估产品定位与政策合规，必要时移除全屏能力。

`NotificationProvider` 在数据加载、事项变化、通知时间或全屏开关变化、恢复前台和应用重新启动时重建计划。从系统设置返回会重新诊断并重排。总开关与全屏开关默认关闭，设置用 SecureStore 保存在当前手机，不加入业务数据库或 Supabase。Web 使用 localStorage 与无发送能力的替身，仅展示手机界面。

## 7. 手机界面

首页保留“日历 / 生日簿 / 时光记”入口，并以 `HomeTab` 驱动动态标题和互斥内容区。日期计算、月历、当天提醒和所选日期事项只属于“日历”；当天提醒卡直接复用 `festivalsOn(today)` 与生日状态，节日和生日重叠时共用一张强调卡片。生日簿和时光记切换后直接渲染各自完整列表，不再在条件内容之前渲染跨标签摘要。手机竖屏中压缩品牌、标题与区块间距，月历先于当天提醒和所选日期面板出现；新增和编辑采用手机页面或模态面板。适配安全区域、键盘遮挡、系统返回和文字放大。

`components/NavigationDrawer.tsx` 提供全局左侧覆盖式功能菜单：首页和设置页共用同一组主要功能及设置入口。首页功能通过回调立即切换 `HomeTab`；从其他页面进入时使用 Expo Router 返回首页并传递 `tab` 或 `tool` 查询参数。重要日期提醒和账号同步分别使用 `/account?section=notifications` 与 `/account?section=account`，`AccountScreen` 只渲染当前区块，避免设置内容相互混杂。电脑的 `preview=phone` 参数在菜单跳转中继续保留。菜单开关、遮罩和各入口均提供明确的无障碍标签。

同日多人的生日全部在事项列表中列出，网格单元只展示有限姓名和数量提示。编辑时读取原始生日，新建时才由选中阳历日期预填。

月历生日名称下方使用独立一行显示 `occurrence.kinds` 对应的“农历”“阳历”，按本次发生类型标注，不根据人物是否同时保存两套日期推断。类型标记可换行，长姓名只在名称行尾部省略；生日区预留相同高度，使有无生日的格子保持日期对齐。`MonthCalendar` 通过 `compact` 属性切换手机密度：手机日期格最低高度为 74 像素，并同步收紧星期栏、日期内边距和生日预留区；宽屏继续使用 100 像素日期格。月历头部固定为单行：可点击的年月标题弹性占用剩余空间，翻月与“今天”操作组不收缩；紧凑布局收窄内部间距并保留每个操作至少 44 像素的触控区域，使一位数和两位数月份在 320—443 像素宽度间切换时不会换行或改变头部高度。

表单提供三种生日方式，复用现有月日选择组件；农历与阳历各有独立输入缓冲，切换方式不丢失当前草稿，保存时只提交启用的日期。补充缺失日期需要主动选择，避免误用当前浏览日期。双生日分别展示下一次预览；详情按时间列出接下来的三次生日并注明类型，同一天重合时合并说明。

## 10. 实施顺序

1. **建立手机工程与运行验证。** 创建 Expo 工程，锁定工具链，打通 Android 开发构建并尽早验证 iOS；小范围验证 SQLite 和农历库在真机的运行。
2. **完成规则与存储。** 实现时区、历法适配器、年度生日计算、数据库迁移和仓库接口，让规则与持久保存通过测试。
3. **实现第一期界面。** 完成月历、生日簿、详情和新建编辑，接入统一状态与真实今天，移除正式流程中的演示数据。
4. **接入账号与同步。** 完成认证、本地数据范围、离线队列、服务端迁移、冲突处理和账号管理。
5. **完成设备验收。** 检查跨午夜、重启保留、失败恢复、账号深链接、跨设备同步和手机交互，完成目标平台发布构建。

当前第 2、3、4 步的代码与自动测试已完成，电脑预览已走通真实 CRUD 和账号入口；第 1 步已完成工程初始化、Android 原生工程生成、双平台 Hermes 资源导出，以及 Android 通用测试 APK 的本地编译、对齐、签名和包信息校验。第 4 步仍需继续完成手机与电脑的真实跨设备同步和注销联调；第 5 步的 Android 安装、启动与设备行为验收待手机连接并授权 USB 调试后执行，iOS 仍需 macOS / Xcode 与测试设备。

iOS 本地构建和模拟器需要 macOS / Xcode；Windows 环境也可选择 EAS Build 云构建，配合真实 iPhone 验证。云服务是可选工具，其账号、签名、费用与分发条件在实际使用时确定，当前未上传工程或发布应用。参见 [Expo FAQ](https://docs.expo.dev/faq/) 与 [EAS Build 文档](https://docs.expo.dev/build/introduction/)。
